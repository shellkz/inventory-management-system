# 已知問題

## entity軟刪除後名稱被永久卡死

vision-service的`RecognitionEntity.name`有DB層`unique=True`約束，軟刪除後名稱會被永久卡死，之後無法重新註冊同名entity。

要修的話：
1. `create_entity`的重複檢查要排除`is_deleted`的列
2. DB層的`unique=True`也要處理，否則即使應用層改了，INSERT時還是會撞SQLite的UNIQUE約束——可以直接拿掉`unique=True`交給應用層把關，或改成SQLite支援的partial unique index(`WHERE is_deleted = 0`)

**相關的另一個成因(錯誤回滾缺失)**:`items/views.py`的`add_item()`裡,`vision_client.create_entity()`跟`vision_client.create_instance()`包在同一個`try`裡,但`create_entity`成功、`create_instance`失敗時(例如vision-service在這之間剛好斷線/重啟),except分支只回502錯誤,沒有補償清理剛剛建立的entity——inventory這邊不會有殘留Item(因為`db.add(item)`在try區塊之後才執行),但vision-service那邊會留下一個沒有對應inventory物品的孤兒entity,一樣會卡住這個名字(即使它是active、不是軟刪除狀態)。實際發生過一次:entity「指甲剪」被建立成功但沒有對應Item,之後重新新增同名物品時在`create_entity`這一步就直接409——已手動刪除該筆殘留entity排除。

要修的話：`create_instance`失敗的except分支要補一個best-effort的`vision_client.delete_entity(entity_id)`,避免留下孤兒。

## 出入庫/盤點傳入不存在的item_id會500

`process_stock_in`/`process_stock_out`/`process_stocktake`都用`db.get(Inventory, item_id)`取庫存列，沒檢查`None`就直接用，傳入不存在的`item_id`會直接撞`AttributeError: 'NoneType' object has no attribute 'quantity'`，整個未攔截，回傳Flask預設的500 HTML頁面，不是這幾支route其他情境用的乾淨JSON錯誤格式(`invalid_json`/`validation_error`/`vision_service_error`那種)。

正常操作下item_id都是前端從已知的catalog選出來的，幾乎不會真的傳入不存在的id，所以一直沒被撞到，但不是正確的防呆行為。

要修的話：三支函式開頭都要加「查不到對應Inventory就擋下來，回傳清楚的錯誤」這一步。
